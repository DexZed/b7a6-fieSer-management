Field Service Management System (FSMS)

Comprehensive functional and technical requirements document for design, development, and delivery.

01. Executive Summary & Project Overview

Core Problem

Small-to-medium field service businesses (e.g., HVAC repair, appliance maintenance, plumbing services) often rely on fragmented communication methods like phone calls, messaging apps, and spreadsheets. This leads to common operational issues:

  • Scheduling Conflicts Double-booking technicians or assigning jobs without considering technician availability.
  • Unclear Status Tracking Customers and dispatchers lack visibility into job progress once a technician departs.
  • Manual Billing Friction Delays between completing service on-site and generating an accurate customer invoice.

Solution

A centralized web application that automates the lifecycle of a service job—from initial request submission to technician scheduling, work order updates, invoice processing, and customer feedback.

Scope & Constraints (5-Day Student/Hobby Scope)

  • Timeframe: 5-day build.
  • Architecture Strategy: Single monolithic application (Node.js/Express, NestJS, Python/FastAPI, or Ruby on Rails) coupled with a relational database (PostgreSQL/MySQL).
  • Out of Scope: Real-time GPS/map tracking, complex routing algorithms, multi-currency support, offline-first mobile sync, payment gateway integration APIs (mock payments used instead).

02. Users & Roles

Role Primary Responsibilities Scope & Permissions
Customer Submits service requests, views work order status, approves invoices, submits feedback. Own profile, own service requests, own invoices.
Dispatcher / Manager Reviews requests, manages technician availability, assigns jobs, overrides schedules. Full access to Work Orders, Scheduling, and Customers.
Technician Views assigned daily schedule, updates work order status (Started, Completed), adds service notes. Assigned Work Orders, limited profile/skill editing.
Finance / Admin Manages job invoicing, marks payments received, views financial reports. Access to Invoices, Payments, and Financial Analytics.
Admin System configuration, user account management, master reference data. Unrestricted global access.

03. Main Workflows

3.1 Service Request to Work Order Lifecycle

 Customer            Dispatcher          Technician          Finance
    │                   │                   │                   │
    ├── Create Request ──>                  │                   │
    │   (Status: PENDING)                   │                   │
    │                   ├── Review & Approve ──>                │
    │                   │   Assign Tech/Time  │                 │
    │                   │   (Status: ASSIGNED)│                 │
    │                   │                   ├── Update: IN_PROGRESS
    │                   │                   │   Add notes/parts │
    │                   │                   ├── Update: COMPLETED
    │                   │                   │   (Generates Invoice)
    │                   │                   │                   ├── Process Payment
    │                   │                   │                   │   (Status: PAID)
    ├── Leave Review ────>                  │                   │
  1. Request Submission: Customer creates a Service Request with job location, description, and preferred time frame.
  2. Review & Scheduling: Dispatcher reviews the request, converts it to a Work Order, selects a Technician based on skill, checks for schedule conflicts, and sets a scheduled start/end time.
  3. Execution:
    • Technician views their schedule.
    • Upon arriving on-site, Technician changes status to IN_PROGRESS.
    • Upon job completion, Technician updates status to COMPLETED and enters resolution notes and billable items.
  4. Invoicing & Payment: System generates an Invoice linked to the completed Work Order. Customer or Finance processes payment (mocked transaction).
  5. Feedback: Customer fills out a post-service rating and review.

04. Database Entities & Relationships

Entity Relationship Description

  • User 1 : N ServiceRequest (A customer can make multiple requests).
  • User 1 : N WorkOrder (A technician can be assigned to multiple work orders).
  • WorkOrder 1 : 1 ServiceRequest (Each approved request creates one work order).
  • WorkOrder 1 : 1 Invoice (Each work order produces one invoice).
  • WorkOrder 1 : 1 Feedback (Each completed work order can have one review).
  • User M : N Skill (Technicians can have multiple skills; handled via TechnicianSkill).

Schema Draft

-- Core Users Table
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    full_name VARCHAR(100) NOT NULL,
    role VARCHAR(20) NOT NULL CHECK (role IN ('CUSTOMER', 'TECHNICIAN', 'DISPATCHER', 'FINANCE', 'ADMIN')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Skills Reference Data
CREATE TABLE skills (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) UNIQUE NOT NULL
);

-- Join table for Technician Skills
CREATE TABLE technician_skills (
    technician_id INT REFERENCES users(id) ON DELETE CASCADE,
    skill_id INT REFERENCES skills(id) ON DELETE CASCADE,
    PRIMARY KEY (technician_id, skill_id)
);

-- Service Requests submitted by Customers
CREATE TABLE service_requests (
    id SERIAL PRIMARY KEY,
    customer_id INT REFERENCES users(id),
    title VARCHAR(150) NOT NULL,
    description TEXT NOT NULL,
    address VARCHAR(255) NOT NULL,
    status VARCHAR(20) DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED', 'CANCELLED')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Work Orders generated after dispatcher review
CREATE TABLE work_orders (
    id SERIAL PRIMARY KEY,
    request_id INT UNIQUE REFERENCES service_requests(id),
    technician_id INT REFERENCES users(id),
    dispatcher_id INT REFERENCES users(id),
    status VARCHAR(20) DEFAULT 'ASSIGNED' CHECK (status IN ('ASSIGNED', 'IN_PROGRESS', 'COMPLETED', 'CANCELLED')),
    scheduled_start TIMESTAMP NOT NULL,
    scheduled_end TIMESTAMP NOT NULL,
    completion_notes TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Invoices linked to Work Orders
CREATE TABLE invoices (
    id SERIAL PRIMARY KEY,
    work_order_id INT UNIQUE REFERENCES work_orders(id),
    amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) DEFAULT 'UNPAID' CHECK (status IN ('UNPAID', 'PAID', 'CANCELLED')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Payments
CREATE TABLE payments (
    id SERIAL PRIMARY KEY,
    invoice_id INT REFERENCES invoices(id),
    amount_paid DECIMAL(10, 2) NOT NULL,
    payment_method VARCHAR(50) DEFAULT 'CREDIT_CARD',
    paid_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Customer Feedback
CREATE TABLE feedback (
    id SERIAL PRIMARY KEY,
    work_order_id INT UNIQUE REFERENCES work_orders(id),
    rating INT CHECK (rating BETWEEN 1 AND 5),
    comments TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

05. Business Rules

  1. Scheduling Constraints:
    • A Technician cannot be assigned to overlapping time slots (scheduled_start to scheduled_end).
    • scheduled_end must be strictly after scheduled_start.
  2. Work Order State Transitions:
    • Valid transitions: ASSIGNED $\rightarrow$ IN_PROGRESS $\rightarrow$ COMPLETED.
    • Reverting from COMPLETED back to IN_PROGRESS is disabled to prevent billing inconsistencies.
  3. Invoicing Logic:
    • An Invoice is generated automatically upon transitioning a Work Order to COMPLETED.
    • Changing job details post-completion requires Admin or Finance override.
  4. Cancellation Rules:
    • Customers can cancel a Service Request only while it is in PENDING status.
    • Once a job is IN_PROGRESS, only a Dispatcher or Admin can cancel it.

07. Transaction Boundaries

To maintain database consistency without external message queues, wrap related operations in database transactions (BEGIN ... COMMIT / ROLLBACK):

  1. Work Order Creation & Request Approval:
    • Operations: Update service_requests.status to 'APPROVED' AND Insert new record into work_orders.
    • Failure behavior: If inserting into work_orders fails (e.g., schedule conflict validation), roll back the request status update.
  2. Job Completion & Invoice Generation:
    • Operations: Update work_orders.status to 'COMPLETED' AND Create entry in invoices with baseline labor/parts cost.
    • Failure behavior: If invoice creation fails, the work order status must not update to COMPLETED.
  3. Payment Processing:
    • Operations: Insert into payments AND Update invoices.status to 'PAID'.

08. Caching Strategy (5-Day Simplified Scope)

Given the short development window, keep caching minimal and localized to avoid stale data during scheduling:

  • In-Memory / Application Level: Cache static reference data (e.g., skills list) in application memory or Redis (if already configured).
  • No Heavy Caching for Work Orders: Work order status and schedules change frequently. Query these directly from the database using indexed queries (WHERE technician_id = ? AND scheduled_start >= ?) to guarantee real-time accuracy for dispatching.
  • HTTP Cache Headers: Disable aggressive browser caching for /api/work-orders endpoints using standard headers (Cache-Control: no-store).

09. Admin Operations & Maintenance

  • User & Skill Management
    • Create, update, or deactivate Technician profiles.
    • Add/Edit skill categories (e.g., "HVAC", "Plumbing", "Electrical").
  • Manual Schedule Overrides

    Dispatchers/Admins can reassign a Work Order to a different technician or force-reschedule a time slot if an unexpected emergency occurs.

  • System Diagnostics

    Basic endpoint (GET /api/health) returning DB connection status and server uptime.

10. Analytics & Reporting (Minimal Viable Dashboard)

Keep reports limited to simple aggregate SQL queries:

  1. Technician Utilization / Job Count:

    Total completed jobs per technician over a selected date range.

    Query: COUNT(work_orders.id) grouped by technician_id where status = 'COMPLETED'.
  2. Revenue Summary:

    Total paid vs. unpaid invoice amounts.

    Query: SUM(amount) grouped by status from invoices.
  3. Customer Satisfaction:

    Average rating score per technician or overall system average.

    Query: AVG(rating) joined across work_orders and feedback.

11. Important Edge Cases & Handling Strategy

1. Schedule Overlaps (Double-Booking)

Issue: Two dispatchers attempt to assign the same technician to different jobs at overlapping times.

Handling: Use a database check or SQL conditional insert checking: WHERE technician_id = :id AND scheduled_start < :new_end AND scheduled_end > :new_start. Reject with a 409 Conflict status code.

2. Technician No-Show / Overdue Job

Issue: Job scheduled time passes, but status is still ASSIGNED.

Handling: Display an "Overdue" visual indicator on the Dispatcher dashboard if NOW() > scheduled_end and status != 'COMPLETED'.

3. Simultaneous Status Updates

Issue: Technician completes a job at the same time a dispatcher tries to cancel it.

Handling: Use basic optimistic locking (check updated_at or current status in the UPDATE query clause).

4. Deleting Users with Active Jobs

Issue: Attempting to delete a Technician account assigned to pending work orders.

Handling: Soft-delete users (is_active = false) instead of hard database deletions to maintain foreign key integrity.
